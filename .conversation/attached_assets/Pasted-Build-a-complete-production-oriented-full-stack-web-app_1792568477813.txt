Build a complete, production-oriented full-stack web application called:

"Windows Automation Portal"

PURPOSE
=======

I have:

1. One Linux server that will run Ansible.
2. One Windows Server where existing PowerShell scripts are stored.
3. Users need a web UI where they can:
   - Choose an approved automation.
   - Enter the required parameters.
   - Submit the request.
   - Track execution status.
   - View sanitized results.
   - View previous execution history.
4. The backend must validate the request and execute an approved Ansible playbook.
5. Ansible must connect from the Linux server to the Windows Server using WinRM over HTTPS.
6. The Ansible playbook must call a predefined PowerShell script located on the Windows Server.
7. Every automation run must be recorded in a PostgreSQL database.

IMPORTANT EXECUTION ENVIRONMENT
===============================

The application may be developed and previewed in Replit, but production Ansible execution will happen on my Linux automation server.

The project must therefore support two execution modes:

1. MOCK_MODE=true
   - Used in Replit and local development.
   - Must simulate Ansible and PowerShell execution.
   - Must not require access to a real Windows Server.
   - Must simulate pending, running, successful, failed, and timed-out jobs.
   - The complete UI, API, database, job status, logs, and history must work in mock mode.

2. MOCK_MODE=false
   - Used on the Linux automation server.
   - Must execute real Ansible playbooks.
   - Must connect to the Windows Server through WinRM over HTTPS.
   - Must run approved PowerShell scripts.
   - Must capture Ansible output, status, timing, and sanitized errors.

Do not claim to have tested real WinRM connectivity from Replit. Clearly explain that real execution must be tested from the Linux server, where the Windows Server is network-accessible.

JOB EXECUTION DESIGN
====================

Do not keep a long-running Ansible subprocess inside a normal HTTP request.

Implement an internal background job runner suitable for the initial version:
- Job submission immediately creates a database job record.
- API returns HTTP 202 with the job ID.
- Background worker picks up pending jobs.
- Worker updates status and job events.
- Frontend polls job status and events.
- Apply configurable concurrency limit.
- Apply job timeout.
- Recover jobs that were left running after application restart by marking them failed or re-queueing according to a documented policy.
- Use database-backed locking so the same job is not executed twice.
- Add graceful shutdown logic.

Create the worker as a separate process or command, for example:
- python -m app.worker

Docker Compose and production instructions must run the API and worker separately.
